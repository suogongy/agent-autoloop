# 收编「飞书私聊提需求」为内置插件 feishu-in

## Context

用户希望：在飞书私聊机器人发消息 = 提需求；追问在同一会话继续，`/new` 后开新会话。本机两个实例（3350/3351）已各有一份手拷的本地原型 `~/.agent-autoloop*/plugins/feishu-in/channel.ts`（今日部署验证过链路），但无测试、无文档、两份拷贝手动同步。本批把它收编进仓库为内置插件，补齐测试与文档。协议零改动——事件仍走 `POST /v1/events` + 来源密钥，内核不认识飞书。

概念对照（已向用户解释）：事项=规则+subject 的调度单位；`resume: true` 使同事项续会话；会话历史在 Agent 侧，中台只存 session id。

用户已拍板：A 路线（独立内置插件）；私聊校验发送者；会话式处理（默认追问同会话、`/new` 开新会话）。

## 设计

**`plugins/feishu-in/channel.ts`（新，channel 类，只收消息不投卡片）**

以 `~/.agent-autoloop/plugins/feishu-in/channel.ts` 为底子收编，保持其已验证行为：
- `lark-cli event consume im.message.receive_v1 --as bot` 长连接收消息，断线 10 秒重起；
- 私聊（p2p）→ 事件 `{ id: "req-<messageId>", type: "request.new", summary/detail 为消息文本（200/4000 截断）}`；
- `alerts` 列表里的群 chat_id → `alert.report`，subject 为 chat_id，`whitelist` JSON 文件过滤（每次重读，改文件即生效）；
- `discover: true` 时把不认识的消息形状/chat 记进日志；
- 心跳：每分钟 `hub.nextCard(1)`，误入的卡片报 `failed`；
- 事件用 `fetch` + `sourceKey` POST 到 `options.url` 的 `/v1/events`，依赖中台按 (source,id) 去重，重发安全。

在原型基础上新增两点：
1. **发送者校验**：config.json 通道选项 `users: ["ou_…"]`。私聊消息从 lark-cli 事件流提取发送者 open_id（防御式多层取值：`event.sender.sender_id.open_id ?? event.sender_id ?? …`，与原型 `messageOf` 同一手法，配 discover 日志兜底）；不在名单 → 记日志、不发事件。`users` 缺失或空 → 不收任何私聊并 log 提示配置（校验从严）。
2. **`/new` 会话轮换**：trim 后精确等于 `/new` 的私聊不发事件；改为把该发送人的 epoch +1，持久化到 `$AGENT_AUTOLOOP_HOME/feishu-in-epochs.json`（`{ openId: epoch }`，读写容错：文件坏了当 `{}` 起步）。subject 规则：epoch 1 → `<openId>`，之后 → `<openId>-<epoch>`（均满足 subject 字符集 `^[A-Za-z0-9#._:/@-]*$`）。下一句话落进新 lane/新事项，配合规则的 `resume: true` 即新会话；旧事项与旧会话原样留在历史。

收编清理：内置插件可 import 引擎文件——删掉原型自带的 `eachLine`，改用 `host/lines.ts`；`safeJson` 等小工具若引擎已有则复用（`plugins/feishu/channel.ts:12` 有同名实现，但它是插件目录非引擎目录，不强求跨插件复用，保留本地小函数）。

**配套规则示例（写进 plugins.md）**

```jsonc
// rules.json
"sources": { "feishu-in": { "name": "飞书需求" } },
"channels": { "feishu-in": { "name": "飞书收件", "answerers": ["ou_xxx"] } },
"rules": [{ "name": "飞书提需求",
  "when": { "source": "feishu-in", "types": ["request.*"] },
  "to": "claude", "cwd": "~/code/project", "skill": "dev-flow",
  "parallel": 2,   // 按 subject（发送人/epoch）分事项
  "resume": true,  // 同事项追问接着上一轮会话
}]
// config.json
"channels": { "feishu-in": { "key": "<通道密钥>", "lark": "<lark-cli 绝对路径>",
  "url": "http://127.0.0.1:3350", "sourceKey": "<feishu-in 来源密钥>",
  "users": ["ou_xxx"], "alerts": ["oc_群chat_id"], "whitelist": "…/alerts-whitelist.json", "discover": true } }
```

## 文件清单

- `plugins/feishu-in/channel.ts` — 新插件（先写测试再实现）
- `tests/feishu-in.test.ts` — 新测试文件，文件头注明防的失败方式。沿用 `tests/channels.test.ts` 的假 lark-cli 模式（shell/`#!node` 脚本经 `options.lark` 传入，`event consume` 流出 JSON 行），加一个本地 `node:http` 服务收 `POST /v1/events` 断言鉴权头与事件体。覆盖：①私聊成事件（含 id/type/subject/截断）②名单外发送者被拒、`users` 缺失全拒 ③群命中白名单不派、未命中派发 ④`/new` 轮换 epoch 且不发事件、重启插件（重新调用默认导出）后 epoch 沿用文件值 ⑤discover 记录未知形状 ⑥误路由卡片报 failed
- `docs/plugins.md` — 通道插件节加「飞书收件（feishu-in）」小节：定位（只收不发）、选项表、上面的规则示例、会话与 `/new` 的用法说明
- `INSTALL.md`、`skills/agent-autoloop/SKILL.md` — 飞书段落补一句：收私聊需求需在开发者后台订阅 `im.message.receive_v1` 并开对应机器人权限；提醒同一应用别开第二个监听
- 部署迁移不在本批代码内，但写在汇报里：两实例升级到含此插件的版本后，把本地拷贝的 options 搬进 config.json 即可删掉 `~/.agent-autoloop*/plugins/feishu-in/`

1. `npm run test:quick`（未动 kernel/protocol/sim 的分流）、`npm run typecheck`、`npm run format:check` 全过。
2. `node --test tests/feishu-in.test.ts` 单独跑过。
3. 真机验证（可选，需用户确认后）：在某实例上用内置插件替换本地拷贝，私聊发一句需求 + 追问 + `/new` + 再提问，观察 `up.log` 中事件序号、runs 的 session 是否按预期续/换。

## 风险与声明

- lark-cli 消息流中发送者 open_id 的确切字段路径未在真机核实过——防御式取值 + discover 日志兜底，真机验证时确认，取不到时按「不在名单」拒绝（安全侧默认）。
- 原型的 `request.new`/`alert.report` 类型名保持不变，两个已部署实例的规则不用改。
